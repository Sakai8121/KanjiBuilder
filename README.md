# 漢字防衛サバイバル（仮）

---

## 🎮 ゲーム概要

DXライブラリ（C++）を用いて制作する、2Dタワーディフェンス・サバイバルゲーム。

制限時間内、あらゆる方向から迫りくる敵から中心のタワー（家）を守り抜く。

最大の特徴として、プレイヤーは「漢字の部首（パーツ）」をグリッド上に組み合わせて防衛キャラクターをビルド（構築）し、その組み合わせに応じたパラメータや挙動で迎撃を行う。

### 開発環境

* **開発環境:** C++, DXLib, Visual Studio 2022
* **想定プレイ時間:** 1ウェーブ数分程度
* **コアメカニクス:** パズル的構築（漢字ビルド） × サバイバル防衛

---

## 🚀 制作段階（ロードマップ）

開発は段階的にイテレーションを回し、常に「動く状態」を維持しながら拡張していく。

### Phase 1: 基本防衛ループと基盤構築（MVP）

* Application, SceneManager, GameObject, Componentシステム等のCore基盤実装。
* 敵のランダムスポーンと、タワーへ向かう移動ロジック。
* タワーからの自動迎撃（最も近い敵を攻撃）。
* JSONパラメータ読み込みとオブジェクトプールの導入。

> **※この段階ではプレイヤーは操作できず、固定キャラ（またはタワー自身）が迎撃する状態**

### Phase 2: アタッシュケースと構築基盤（UI・操作）

* 「構築フェーズ（時間停止）」への状態遷移。
* パーツ一覧（アタッシュケース）のUI実装。
* ドラッグ＆ドロップ操作と、グリッド（マス目）へのスナップ配置。

> **※この段階では配置の見た目と操作感のみを完成させる。**

### Phase 3: 漢字ビルド・ロジック結合

* 隣接パーツの連結判定アルゴリズム（グループ化）の実装。
* 組み合わせに基づくパラメータ（HP、攻撃力、範囲など）の算出とレーダーチャート等での視覚化。
* 構築したキャラクター（パーツ群）による実際の迎撃処理。

### Phase 4: ゲームサイクルの確立（リソース制限）

* 敵からのパーツドロップ（インベントリ管理）。
* パーツごとのクールタイム導入。
* ウェーブの進行や敗北条件等の全体ゲームサイクルの完成。

# 🏗 Architecture / Design Philosophy

本ドキュメントは、ゲーム完成という目的に加え、ゲームエンジンのフレームワークを含めたC++による設計パターンの実践を目的としたプロジェクトの基本方針である。

開発中に設計の選択で迷った際や、制作段階を振り返るための自分用のメモとして書き残しておく。

---

## 1. Core / Game の分離

汎用的なフレームワーク機能を `Core`、ゲーム固有のロジックを `Game` に分離する。

`Core` から `Game` への依存を作らず、ゲーム固有の変更が基盤側に波及しにくい構造を基本とする。

---

## 2. Component指向とOwnership

クラスの継承ツリーが複雑化するのを防ぐため、`GameObject` を単なる器とし、機能は `Component` として分離・アタッチする設計とする。

### 所有と参照

`GameObject` が `Component` を `unique_ptr` で所有（管理）する。生ポインタ・参照は「借用」のみとし、`delete` はしない。

`Component` から親（`GameObject基底`）への参照は、寿命が完全に同期される前提のもと生ポインタ（Raw Pointer）を用い、スマートポインタによる不要なオーバーヘッドを避ける。

### GameObject 同士の参照（Handle）

ターゲットや発射元など、`GameObject` 同士の参照は生ポインタではなく **Handle（index + generation）** で持つ。管理は `SlotMap` が行い、参照先が破棄済みの場合、`Get` は `nullptr` を返す。

> 生ポインタでは、参照先が破棄された後（オブジェクトプールで別のオブジェクトとして再利用された場合を含む）にダングリングポインタとなる。また、`vector` 等の再配置でもアドレスが無効になる。Handle はこれらを `Get` 時の世代チェックで検出できる。

* Handle にするのは、「他から参照される」かつ「寿命が動的」なものだけとする。
* `Get` で得たポインタは、その場で使い切る（保持しない）。

---

## 3. 依存関係に応じた通信方式の選択（目安）

クラス間の結合度をコントロールするため、通信方式の使い分けの目安を以下のように定める。

### 直接参照

明確な上下関係がある場合。

> 例: `EnemyBrain` が `Transform` を操作するなど。

### EventBus

システム全体（Global）を跨ぐ1対多の通知。**まずはこの方式から始める。**

> 例: 敵の死亡をUIやスコア管理へ伝える等。

発行元と受信元がお互いを知る必要のない疎結合を実現するが、処理の追跡が難しくなるため局所的な乱用は避ける。

* **キュー方式とする。** `Publish` は積むだけで、フレーム内の決まった位置で `Flush` する（Update中のコンテナ変更や再入によるバグを防ぐため）。
* イベントは小さな構造体とし、受信側が必要とするデータそのものをコピーして持たせる（受信時に発行元が破棄済みでも困らないようにするため）。
* 購読は RAII の `Subscription` で管理し、購読側の破棄時に自動で解除する。

### Callback（`std::vector`）

オブジェクト内部（Local）での1対多のイベント通知。同一オブジェクト内など、受信側を自分が知っている場合に使う。EventBus から始め、必要になった時点で追加する。

対象オブジェクトを取得し、関数ポインタを直接登録することで型安全かつ高速に処理を連動させる。

---

## 4. Update Order（実行フェーズの分離）

実行順序のズレによるバグを防ぐため、ゲームループ内の処理フェーズは概ね以下の順序を意識して設計する。

1. **Input:** 入力状態の取得。
2. **Update:** 各ロジックの更新（移動量の決定など）。
3. **Physics:** 確定した移動量に基づく当たり判定やダメージ処理。
4. **LateUpdate:** 座標確定後の処理（カメラ追従など）。
5. **EventBus Flush:** 積まれたイベントの配信。
6. **Spawn / Destroy:** 生成・破棄キューの一括処理。
7. **Render:** 画面への描画。

### 生成・破棄の遅延

Update 中の生成・破棄は直接行わず、キューに積み、フレーム末（6）でまとめて処理する。ループ中のコンテナ変更によるバグを防ぐ。

### 時間の扱い

* `dt` は引数で各システムへ渡す。グローバルな `timeScale` は持たない。
* DXLib には `dt` の機能がないため、`GetNowHiPerformanceCount` で計測し、上限（例: 0.1秒）でクランプする。ウィンドウ操作やブレークポイントなどでループが止まった後の巨大な `dt`（敵のすり抜けやタイマーの一括消化の原因）を防ぐ。
* ゲーム内の時間（制限時間、クールタイム、スポーン間隔など）は、すべて `dt` の積算で数える。実時間は使わない。
* UI は、時間停止の影響を受けない（倍率をかけない）クランプ済みの dt で更新する。

```cpp
LONGLONG prev = GetNowHiPerformanceCount();
while (ProcessMessage() == 0) {
    LONGLONG now = GetNowHiPerformanceCount();
    float frameDt = std::min((now - prev) / 1'000'000.0f, 0.1f);
    prev = now;
    sceneManager.Update(frameDt);
    // ...
}
```

### 構築フェーズ

構築フェーズは別シーンにせず、`GameScene` 内のステートマシン（Battle / Build）とする（戦闘中のオブジェクトの破棄・復元を避けるため）。

* Build 中は戦闘側の `world.Update` を呼ばず、時間を停止する。
* UI は時間停止の影響を受けない `frameDt` で更新する。

---

## 5. Data-Driven Design（データ駆動設計）

パラメータの調整を容易にするため、データ駆動を意識する。

設定値（敵のステータス等）はJSON等から読み込むが、`Component` 内で直接ファイル解析をするのではなく、生成を担うクラス（FactoryやManager等）がデータを読み込み、初期化時に必要な数値だけを注入（Dependency Injection）する構成を目指す。

ライブラリの例外（nlohmann/json）は、この読み込み層（Loader / Factory）の中だけで catch し、ログ出力と既定値に変換する。

---

## 6. リソース管理

`ResourceManager` が画像ハンドルをパスで管理し、同じ画像の重複読み込みを防ぐ。

* 解放はシーン単位で行う。
* 読み込みに失敗した場合は `Log` を出し、代替画像を返す。
* `ResourceManager` は `Application` が所有し、使う側には参照を渡す。`DxLib_End()` より前のスコープ内で確実に破棄するため、シングルトンにはしない。

```cpp
int WINAPI WinMain(...) {
    DxLib_Init();
    {
        Application app;   // ResourceManager はこのスコープ内で生成・破棄される
        app.Run();
    }
    DxLib_End();
}
```

---

## 7. パフォーマンス方針

* 最初は、すべてのオブジェクトを `GameObject` で作る。
* 数千個になる弾やエフェクトなど、プロファイルして重いと分かったものだけ、軽量な構造体の配列に差し替える。
* 差し替えられるよう、生成は Factory 経由に統一する。

# 📝 Coding Rules

「ゲームのバグに直結するもの」と「決めておくとコードがきれいになるもの」だけを書く。

## バグに直結するもの

1. **メンバは「依存される側を先に」宣言する。** `Subscription` などの RAII ハンドルは最後に置く。参照で借りる相手は、自分より長生きするものに限る。
   *（メンバは宣言の逆順で破棄されるため）*
2. **DXLib のリソースを持つ、またはデストラクタで DXLib を呼ぶオブジェクトを、static / グローバルにしない。** それらは `DxLib_Init()` 〜 `DxLib_End()` のスコープ内で破棄する。
   *（static の破棄は `DxLib_End()` の後になるため）*
3. **所有は `unique_ptr`、生ポインタ・参照は借用のみで、その場で使い切る（保持しない）。`GameObject` 同士の参照は Handle で持つ。**
4. **Update 中に生成・破棄を直接しない。** キューに積み、フレーム末にまとめて処理する。
   *（ループ中のコンテナ変更を防ぐため）*
5. **プログラマのミスは `assert`、実行時に起きうる失敗は `Log` を出して継続する。** `assert` の中に副作用のある処理を書かない。
   *（`assert` は Release で消える。コードを直せば防げるものは即座に止め、ファイル欠落など防げないものは続行する）*
6. **例外は使わない。** ただし nlohmann/json の例外だけは、読み込み層（Loader / Factory）で catch し、ログ + 既定値にする。
7. **継承を意図しない（仮想デストラクタを持たない）クラスには必ず final を指定する。**
（意図しない継承によるメモリリークや未定義動作をコンパイラレベルで防ぐため）

## コードがきれいになるもの

7. **命名**
   * 型・関数: `PascalCase`
   * 変数: `camelCase`、メンバ変数: `_camelCase`（例: `_hp`）
   * 定数（名前空間・クラススコープの `constexpr`）: `kPascalCase`（`const` 修飾は命名に影響しない）
   * `enum class` のみ使用する。名前空間は `Core::` / `Game::`
8. **純粋なロジック（連結判定、ステータス算出など）は `DxLib.h` に依存させない。**
   *（テストとパラメータ調整をしやすくするため）*
